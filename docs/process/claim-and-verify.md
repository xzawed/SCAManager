# 흐름 — "고쳤다" 를 말하기 전에

> **언제 여는가**: *"닫았다" · "봉인했다" · "해소됐다" · "포함됐다" · "0건이다"* 를
> 사용자·PR 본문·문서에 쓰기 **직전**.
>
> 이 흐름이 생긴 이유: 실수 3건이 전부 **행위를 결과로 보고**한 것이었다.
> 집행자를 붙이고 "붙였다"로, 정정 커밋을 밀고 "정정했다"로, 반례를 막고 "닫았다"로 끝냈다.
> 세 번 다 사실이 아니었고, 세 번 다 **말하기 직전에 한 줄만 실행했으면** 잡혔다.

---

## 1. 무엇을 주장하는지 한 문장으로 적는다

주장을 못 적으면 검증 대상이 없는 것이다. 형태는 셋 중 하나다.

| 주장 유형 | 예 | 2단계에서 쓸 근거 |
|---|---|---|
| **상태** | *"main 에 반영됐다"* · *"0건이다"* | 라이브 조회 |
| **집행** | *"이 가드가 그 규칙을 막는다"* | 뮤테이션 red |
| **종결** | *"fail-open 을 닫았다"* | 뮤테이션 red **+ 외부 적대 검증** |

---

## 2. 유형별 근거를 **실행해서** 얻는다

### 2-a. 상태 주장

```bash
git merge-base --is-ancestor <sha> origin/main   # "머지됐다"
git grep -n "<패턴>" origin/main -- <path>        # "main 에 있다/없다"
gh pr view <n> --json state,mergedAt              # "PR 이 닫혔다"
```

**커밋 해시로 머지를 단언하지 마라.** 이미 머지·삭제된 브랜치에 커밋을 얹으면 고아가 되고,
push 출력은 `* [new branch]` 로 보인다 — 그것이 신호다([traps C6](../../.claude/traps.md)).

### 2-b. 집행 주장

```bash
git add -A                       # ① 기준선을 index 에 고정
<보호 장치를 실제로 깨뜨린다>      # ② 실경로 뮤테이션 (합성 픽스처 불가)
git diff --quiet <file> || echo "mutated != orig OK"   # ③ 적용 확인
pytest <그 가드>                  # ④ red 관측
git checkout -- <file>           # ⑤ ① 로 복원
pytest <그 가드>                  # ⑥ green 복귀 확인
```

**④ 가 green 이면 "가드가 공허하다" 로 결론내기 전에 ② 를 의심한다** —
뮤테이션이 엉뚱한 줄에 갔거나 동작을 안 바꿨을 수 있다([traps B2](../../.claude/traps.md)).

**가드 이름을 규칙 옆에 적는 것은 집행이 아니다.** 그 파일을 열어 **정말 그 규칙을
검사하는지** 확인한다 — `check_red_budget` 은 파일명 실재만 보는 프록시다(스스로 인정).

### 2-c. 종결 주장 — 여기가 가장 자주 틀린다

외부 반례를 받아 고쳤다면 그것만으로 부족하다. `AGENTS.md` §불변식 2-b:

1. 받은 반례의 **클래스를 명명**한다 (예: *"아카이브 내용 공동화"*)
2. 그 클래스의 **다른 인스턴스를 스스로 만들어** red 를 확인한다
3. 그 뒤에야 *"닫았다"* 를 말할 수 있다

실증: Grok 반례(2000자 `X`)를 막고 *"fail-open 을 닫았다"* 고 보고했으나,
서사를 100% 제거하고 지문·인용으로 채우니 **전건 통과**였다.
사용자 결정: 보존 축을 내리고 도달성만 남겼다. 공동화된 아카이브는
이제 설계상 green 이다. 아카이브가 내용을 유지하는지를 기계가 재는 장치는 없다.

---

## 3. 근거가 없으면 주장을 낮춘다

| 못 얻은 것 | 대신 쓰는 표현 |
|---|---|
| 라이브 조회 | `UNVERIFIED:` 접두사 (정책 19 2-phase 게이트) |
| 클래스 인스턴스 red | *"이 뮤테이션을 막았다"* — **"닫았다" 는 금지** |
| 실경로 뮤테이션 | *"정적으로 확인했다"* + 한계 명시 |

**낮춘 주장은 실패가 아니다.** 이 저장소가 반복해 값을 치른 것은 못 한 것이 아니라
**한 것보다 크게 말한 것**이다.

---

## 4. 한계를 같은 문장에 적는다

닫은 것과 **열려 있는 것**을 나란히 적는다. 예:

> 닫은 것은 *삭제* 한 클래스뿐이다. 파일을 남기고 `🔴` 줄만 지우는 우회는 여전히 통과한다.

한계를 적지 않으면 다음 세션이 **닫힌 항목으로 읽고 재점검하지 않는다** —
자기보고가 살아있는 결함을 덮는 형태([traps C6](../../.claude/traps.md)).

---

## 이 흐름이 막지 못하는 것

- **주장을 아예 안 적는 경우** — 검증 대상이 없으면 이 흐름도 발동하지 않는다.
- **근거를 위조하는 경우** — 명령을 안 돌리고 결과만 적으면 아무 축도 못 잡는다.
  방어선은 review-time claim-review 뿐이다.
